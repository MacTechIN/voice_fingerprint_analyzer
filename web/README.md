# VoiceGuard 관리자 대시보드 (Phase 4)

Next.js 15 기반 운영 대시보드. 등록 현황, 인증 로그, 판정 품질 지표를 확인한다
(03_WebApp_Definition.md).

## 빠른 시작

```bash
# 1. 분석 서버를 관리자 토큰과 함께 띄운다
cd ../server
export VG_DATABASE_URL="postgresql://voiceguard:voiceguard@127.0.0.1:54321/voiceguard"
export VG_ADMIN_TOKEN="$(openssl rand -hex 32)"   # 운영에서는 반드시 무작위 값
./run.sh

# 2. 대시보드
cd ../web
cp .env.example .env.local     # VG_ADMIN_TOKEN을 서버와 동일하게 설정
npm install
npm run dev                    # http://localhost:3000
```

**대시보드는 PostgreSQL로 기동된 서버에서만 동작한다.** 인메모리 저장소로 뜬
서버는 통계를 제공하지 않으며, 그 사실을 화면에 명시한다.

## 화면

| 경로 | 내용 |
| :--- | :--- |
| `/` | 요청량·응답 시간·판정 결과 분포·시간대별 추이·점수 히스토그램 |
| `/speakers` | 화자 DB — 등록 현황, 모델/차원, **재등록 필요 여부** |
| `/attempts` | 오딧 트레일 — 원시·정규화 점수 병기, IP, 페이지네이션 |
| `/calibration` | 오프라인 EER·minDCF, 임계값 변경 영향도, 적용 방법 |

## 설계 원칙

### 지표를 오해하지 않게 하는 것이 가장 중요한 일

**운영 로그로는 FAR/FRR을 계산할 수 없다.** 감사 로그에는 판정 결과만 있고 **정답
레이블이 없다** — 검증을 시도한 사람이 실제로 본인이었는지 서버는 알 수 없기
때문이다. 따라서 이 대시보드는 두 종류의 근거를 엄격히 구분한다.

| 근거 | 출처 | 말할 수 있는 것 |
| :--- | :--- | :--- |
| **오프라인 캘리브레이션** | `eval/` (레이블 있음) | EER, minDCF, 임계값 결정 |
| **운영 로그** | `verification_attempts` | 점수 분포, 임계값 변경 시 뒤집히는 건수 |

`/` 화면의 "판정 통과율"은 **정확도가 아니다.** 사용 패턴 지표이며, 서버가 응답에
실어 보내는 경고 문구를 화면에 그대로 노출한다.

### 대시보드가 DB에 직접 붙지 않는다

03 문서는 Supabase 직접 접근을 상정했지만, 집계 질의를 서버의 관리자 API로 옮겼다.
이유는 두 가지다.

1. **스키마 지식을 한 곳에 모은다.** 웹 계층이 테이블 구조를 알면 마이그레이션할
   때마다 두 곳을 고쳐야 한다. 실제로 Phase 6에서 `vector(192)` → `vector` 변경이
   있었고, 그때 서버만 고치면 됐다.
2. **DB 자격증명을 웹 티어에 두지 않는다.** 대시보드는 관리자 토큰만 안다.

### 관리자 토큰은 브라우저로 나가지 않는다

모든 페이지가 서버 컴포넌트이며 API 호출도 서버에서만 한다. 환경변수에
`NEXT_PUBLIC_` 접두사를 쓰지 않는 것이 이를 강제한다.

서버 쪽은 **토큰 미설정 시 관리자 API를 503으로 막는다.** 감사 로그와 사용자 ID가
노출되는 경로이므로, 설정을 빠뜨린 배포가 조용히 공개되는 것보다 아예 막히는
편이 안전하다.

### 임계값 런타임 변경 API를 만들지 않았다

FR-11은 "관리자가 임계값을 조정·배포"를 요구한다. 대시보드는 **조정 근거**(오프라인
EER·minDCF, 변경 영향도)와 **적용 방법**(환경변수 스니펫)을 제공하되, 값을 원격에서
바꾸는 API는 두지 않았다. 인증 파라미터를 네트워크로 변경할 수 있게 하는 것 자체가
공격면이기 때문이다. 변경은 환경변수 수정 + 재시작으로 한다.

## 검증

```bash
npx tsc --noEmit    # 타입 검사
npm run build       # 프로덕션 빌드 (4개 라우트, First Load JS 105kB)
```

실제 서버(WeSpeaker 백엔드, Postgres, 코호트 310개)에 연결해 4개 페이지가 모두
실데이터로 렌더링되는 것을 확인했다. 화자 DB가 192차원 SpeechBrain 등록자 2명을
"재등록 필요"로 정확히 표시했고, 캘리브레이션 화면이 EER 1.25%(K=200)에 "적용 중"
배지를 붙였다.

## 알려진 제약

- **자동 새로고침이 없다.** 페이지를 다시 열어야 최신 데이터가 보인다. 03 문서의
  "실시간 시각화"는 폴링이나 SSE가 필요하며, 요청량이 늘어난 뒤에 붙이는 것이 맞다.
- **차트를 CSS 막대로 그렸다.** 차트 라이브러리를 넣지 않았다. 현재 지표(막대·히스토그램)에는
  충분하고 번들이 가볍지만, DET 곡선처럼 곡선형 시각화가 필요해지면 라이브러리를 검토한다.
- **관리자 계정 체계가 없다.** 단일 공유 토큰이며 누가 무엇을 봤는지 기록하지 않는다.
  실서비스에서는 관리자별 계정과 접근 감사가 필요하다.
- **Phase 7~8 지표는 아직 없다.** 03 §5의 전처리 품질(SI-SNRi), 스푸핑 탐지 로그와
  경보는 해당 기능이 서버에 들어온 뒤 추가한다.
