# 긴 소스는 「쪼개서 먼저 처리」 — 청크 선처리·재사용 패턴

> 다른 프로젝트에서 참조하기 위한 설계 문서. 원본 구현은 SEP v2 / LEP v2.
> 원 메모리: `chunked_analysis.md` (SEP 워크스페이스). 최초 해결 2026-08-05, 정리 2026-08-31.

장시간 미디어(녹음·영상)나 큰 입력을 **모델에 통째로 넣지 않는다.**
**조각으로 나눠 · 먼저 전사(선처리)하고 · 뒤 단계는 그 결과를 재사용한다.**

---

## 1. 언제 이 패턴이 필요한가

셋 중 하나라도 해당하면 검토한다.

- **모델 입력 한도를 넘는다.** 예: OpenAI STT 입력 한도 **23분 20초** — 30~60분 미팅은
  자르지 않으면 분석 자체가 안 된다.
- **같은 소스를 여러 번 처리한다.** 분석 → 재분석 → 리포트 재생성. 매번 STT 를
  다시 하면 시간·비용이 반복된다 (실측: 54.6분 미팅 재분석 **약 25분·$1.15** 재지출).
- **서버가 소스를 가공할 수 없다.** 예: Cloudflare Workers 에는 ffmpeg 가 없다 —
  **자르는 일을 할 주체가 서버가 아니다.**

---

## 2. 세 규칙

### 규칙 1 — 자르는 주체를 먼저 정한다

서버가 자를 수 없으면 **입력 지점(브라우저·클라이언트)에서 자른다.**
SEP/LEP 은 브라우저 `MediaRecorder` 가 **10분 조각 + 15초 겹침**으로 녹음한다.
서버(Workers)는 조각을 받기만 한다.

> 겹침(overlap)을 두는 이유는 §5. 안 두면 조각 경계에서 화자·문장이 잘린다.

### 규칙 2 — 조각을 「먼저」 전사하고 저장한다 (선처리)

녹음/업로드가 **끝나기 전에**, 이미 들어온 조각부터 전사해 **저장**한다.
그러면 분석 단계는 그 조각의 전사를 **다시 하지 않고 건너뛴다.**

실측: 선처리된 조각은 분석에서 STT 약 **90초 → 즉시**.

### 규칙 3 — 뒤 단계는 저장된 전사를 재사용한다 (재처리 금지)

분석·재분석·리포트 재생성은 **원본을 다시 전사하지 않는다.**
저장된 조각 전사를 읽어 이어 붙이고, 그 위에서만 작업한다.

---

## 3. 데이터 흐름

```
[입력측이 자른다]        [먼저 전사·저장]              [뒤 단계는 재사용]
 녹음/업로드              조각별 STT                    분석·재분석·재생성
   │  10분+15초 겹침        │                              │
   ├─ 조각1 ──────────────▶ transcribe ──▶ 저장 ┐         │
   ├─ 조각2 ──────────────▶ transcribe ──▶ 저장 ┼──▶ [병합] ──▶ 작업
   └─ 조각N ──────────────▶ transcribe ──▶ 저장 ┘    (겹침 정렬·   (STT 재실행 없음)
                                                       중복 제거)
```

저장 테이블(예): `meeting_chunk_transcripts (meeting_id, chunk_index, storage_path, text, …)`

---

## 4. **안전장치 — 이걸 빼면 조용히 오염된다**

재사용 패턴의 유일하고 치명적인 함정:

> **오디오를 다시 올리면 조각 인덱스(chunk_index)가 겹친다.**
> 인덱스만 보고 재사용하면 **옛 녹취를 새 오디오의 것으로** 붙인다. 오류가 안 나서 안 보인다.

**반드시**: 저장된 전사에 `storage_path`(또는 소스 해시)를 함께 두고,
재사용 전에 **지금 소스의 것과 대조**한다. 안 맞으면 재사용하지 말고 다시 전사한다.

---

## 5. 조각 경계 처리 — 겹침 정렬

10분씩 잘라 각자 전사하면, STT 는 **조각마다 화자 A·B·C 를 새로 매긴다.**
조각1의 「A」와 조각5의 「A」는 아무 관계가 없다.

- **격리**: 우선 조각 경계에서 화자를 분리한다 (`P<조각>:<화자>`). 잘못 합치는 것부터 없앤다.
- **다시 잇기**: 15초 겹침 구간에서 **같은 문장이 양쪽 조각에 나오면** 같은 사람으로 잇는다.
  **근거가 없으면 잇지 않는다.** 갈린 채 두는 게 잘못 합치는 것보다 낫다.
- 겹침이 **없는** 소스(다른 도구로 만든 녹음)는 이을 방법이 원리적으로 없다 —
  그때는 화자가 조각 수만큼 갈린다. 그건 버그가 아니라 입력의 한계다.
  **화면·로그에 「못 이었다」를 남겨** 사람이 「실제 인원」으로 오해하지 않게 한다.

> 실측 사고: 겹침 없는 8조각 녹음이 실제 2명인데 **화자 45명**으로 나왔다.
> 원인은 겹침 부재(못 이음) + 역할 판정 누락 + 「못 이었다」가 화면에 안 보인 것 — 셋이 겹쳤다.

---

## 6. 검증 체크리스트 (구현했다면 이걸로 확인)

- [ ] 한도 초과 소스가 조각 분할로 **분석까지 완료**되는가 (실측: 24.3분→3조각, 54.6분→6조각)
- [ ] 조각 경계 **틈 0ms** · 병합 세그먼트 수가 맞는가
- [ ] **재분석 일관성** — 두 번 돌려 세그먼트 시간 **역행 0건**
- [ ] 선처리된 조각을 분석이 **건너뛰는가** (STT 재실행 안 함)
- [ ] **`storage_path` 대조** — 소스를 바꿔 올렸을 때 옛 전사를 재사용하지 **않는가** ← §4
- [ ] 겹침 없는 소스에서 「못 이었다」가 **기록·표시**되는가 ← §5
- [ ] 짧은 조각 테스트 훅이 있는가 (예: `?chunkMin=1` 로 컷 간격을 1분으로)

---

## 7. 아직 안 된 것 (원본 프로젝트 기준, 참고)

**재분석 STT 재사용이 미구현.** 선처리 저장은 *녹음 중에만* 일어나고,
분석이 전사한 결과는 버려진다 → 재분석은 STT 를 처음부터 다시 한다.
`stepTranscribeChunk` 가 전사를 `meeting_chunk_transcripts` 에도 저장하면
「리포트 재생성」이 STT 없이 1~2분에 끝난다. **재사용 경로와 테이블은 이미 있다.**
(재분석을 트랜잭션·묶음삽입으로 5초로 줄인 건 DB 삽입 최적화이지 STT 재사용이 아니다.)

## 8. 한 줄 요약

**긴 소스는 입력측에서 겹쳐 자르고 · 조각을 먼저 전사해 저장하고 · 뒤 단계는
`storage_path` 로 대조해 재사용한다. 못 이은 것은 숨기지 말고 기록한다.**
