# 06_Development_Plan.md
# 개발 계획서 (Micro-process & Vertical Stackable)

앱 경량화를 목표로 하므로, **API 서버 우선 구축 후 클라이언트를 연동하는 방식**으로 스택을 쌓아 올립니다. Phase 1~5는 프로토타입(Phase A) 완성 경로이며, Phase 6~8은 연구 보고서(『음성 분리 및 화자 대조』)의 4단계 기술 로드맵 — ① 전처리·분리 프론트엔드, ② 초구면 잠재 공간 최적화, ③ 분리 왜곡 극복·AS-Norm 백엔드, ④ 보안 방어막 — 을 단계적으로 반영하는 확장 경로입니다.

## Phase 1: AI 서버 구축 및 API 설계 (Week 1-2) — ✅ 완료

*   *Micro-process:* Python(FastAPI) 기반으로 ECAPA-TDNN 모델 로드 환경 구성. 파이프라인 최전단에 Silero VAD 결합 (무음·소음 구간 제거 후 임베딩 추출).
*   *Output:* 오디오 파일을 업로드하면 임베딩 벡터(모델 기본 차원, ECAPA-TDNN 기준 192차원)를 반환하는 `POST /extract` API 완성. 유효 발화 길이 미달 시 사유 코드 반려 응답 포함.

### 구현 결과 (`server/`)

| 항목 | 결과 |
| :--- | :--- |
| 엔드포인트 | `POST /api/v1/extract`, `GET /api/v1/health` |
| 파이프라인 | 디코딩(16kHz/Mono 정규화) → Silero VAD → ECAPA-TDNN |
| 임베딩 | 192차원, L2 정규화, `model`·`dim` 메타데이터 동봉 |
| 반려 사유 코드 | 6종 (`empty_file`, `file_too_large`, `unreadable_audio`, `audio_too_long`, `no_speech_detected`, `speech_too_short`) |
| 테스트 | 22개 통과 (모델 모킹 없이 실측) |
| 실측 성능 | 7초 오디오 처리 359ms, 서버 기동 4초(모델 선적재 포함) |

**구현 중 확정한 설계 판단**

*   **반려는 5xx가 아니라 422다.** 발화 부족·무음은 서버 장애가 아니라 입력 문제이며, 클라이언트는 `code`별로 다른 재녹음 안내를 띄운다(04 §4). 사유 코드 값은 클라이언트 계약이므로 변경 금지 대상이다.
*   **응답을 `audio`/`embedding` 중첩 객체로 묶었다.** 최상위를 평평하게 두면 Phase B~D에서 `normalized_score`·`spoof_score`가 붙을 때 계약이 지저분해진다(01 §2 확장 여지).
*   **임베딩을 저장 전 L2 정규화한다.** 이후 코사인 유사도를 내적만으로 얻는다(Phase 2 스코어링 단순화).
*   **추론은 워커 스레드로 넘긴다.** CPU 바운드 작업이 GIL을 잡으면 이벤트 루프가 다른 요청의 I/O를 처리하지 못한다.
*   **규격 외 입력(44.1kHz 스테레오 등)도 서버가 흡수한다.** 단 리샘플링은 선형 보간이므로 품질이 중요하면 클라이언트를 고치는 것이 맞다.

**해결한 의존성 충돌 2건** (requirements.txt에 고정, speechbrain 업그레이드 시 재검토)

*   `huggingface-hub` 1.x가 `use_auth_token` 인자를 제거했으나 speechbrain 1.0.2가 아직 사용 → `0.26.5`로 고정.
*   `requests`를 speechbrain이 런타임에 쓰면서 의존성으로 선언하지 않음 → 직접 추가.

## Phase 2: Vector DB 통합 및 인증 로직 (Week 3-4) — ✅ 완료

*   *Micro-process:* Supabase pgvector 구축 (임베딩 모델명·버전·차원 메타데이터 컬럼 포함). 두 오디오 벡터를 비교해 % 확률을 도출하는 코사인 유사도 로직 작성.
*   *Vertical Slice:* 서버 단독으로 등록(`POST /enroll`) 및 검증(`POST /verify`) API 엔드투엔드 작동 확인.
*   *설계 원칙:* 응답 JSON은 확장 가능 스키마로 설계 (추후 `normalized_score`, `spoof_score` 등 필드 무중단 추가 대비).

### 구현 결과 (`server/`)

| 항목 | 결과 |
| :--- | :--- |
| 엔드포인트 추가 | `POST /api/v1/enroll`, `POST /api/v1/verify` |
| 스키마 | `speaker_enrollments`(vector(192) + model·dim 메타데이터), `verification_attempts`(감사 로그) |
| 저장소 | PostgreSQL 16 + pgvector, 인메모리 폴백 (동일 계약) |
| 반려 코드 추가 | `not_enrolled`, `model_mismatch` |
| 테스트 | 51개 통과 (Postgres 계약 테스트 포함) |
| 실측 성능 | 등록 415ms, 검증 273ms |

**구현 중 확정한 설계 판단**

*   **모델 불일치는 조용히 넘기지 않는다.** 등록 성문이 현재 임베딩 모델과 다르면 `model_mismatch`로 거부한다. 차원만 같고 모델이 다른 벡터를 비교하면 무의미한 유사도가 나오는데, 그 값이 그대로 인증 판정에 쓰이기 때문이다(02 §6).
*   **재등록은 삭제가 아니라 비활성화다.** 재등록 후 문제가 생겼을 때 이전 벡터를 추적할 수 있어야 하고, 감사 로그가 참조하는 이력이 사라지면 안 된다.
*   **다중 등록 시 평균이 아니라 최대 유사도로 판정한다.** 평균 벡터는 발화 조건이 다른 벡터들을 뭉개 어느 쪽과도 덜 닮은 중심을 만들 수 있다. 평균 성문은 01 §2의 향후 보강 후보로 유지.
*   **유사도 계산을 SQL이 아닌 애플리케이션에서 한다.** 1:1 검증은 사용자당 소수 벡터만 비교하므로 SQL로 넘길 이득이 없고, Phase 6에 AS-Norm이 들어오면 어차피 스코어 후처리를 애플리케이션에서 해야 한다. 1:N 식별 도입 시 `<=>`와 HNSW로 옮긴다.
*   **`match_probability`는 확률이 아님을 문서·코드에 명시했다.** 판정 경계를 50%에 맞춘 구간 선형 재척도이며, `verification_attempts.normalized_score`는 Phase 6 자리로 비워 두었다(가짜 값을 채우지 않음).
*   **저장소는 실패 시 기동을 중단한다.** 모델 워밍업과 달리 저장소 없이는 등록·검증이 성립하지 않으므로, 반쯤 동작하는 서버를 띄우는 것보다 즉시 실패하는 편이 낫다.

### ⚠ Phase 6까지 유효한 경고

임계값 `0.25`는 **SpeechBrain 관례값일 뿐 본 시스템 데이터로 캘리브레이션한 값이 아니다.** E2E 검증에서 음향적으로 다른 합성 음원이 코사인 0.394로 임계값을 넘어 `is_verified=true`가 나왔다. 합성음이라 화자 인식 성능 자체를 재는 상황은 아니지만, **고정 임계값 판정의 취약성을 그대로 보여준다**(02 §4.2가 예고한 문제). 실제 운영 임계값은 Genuine/Impostor 분포를 모아 EER·minDCF로 결정해야 하며, 그전까지 판정 결과를 신뢰해서는 안 된다.

## Phase 3: 경량화된 Cross-Platform App 개발 (Week 5-7) — ✅ 완료

*   *Micro-process:* Flutter 프로젝트 세팅, 마이크 제어 및 오디오 파일화 로직 구현 (16kHz/Mono 캡처, 최소 3초 발화 강제, 입력 레벨 피드백).
*   *Vertical Slice:* 앱 UI에서 버튼을 눌러 녹음 후 API로 전송하여 화면에 결과를 출력하는 E2E 통신 완성.

### 구현 결과 (`app/`)

| 항목 | 결과 |
| :--- | :--- |
| 플랫폼 | Android · iOS · Linux · macOS · Windows (단일 코드베이스) |
| 화면 | 등록/인증 전환, 발화 스크립트, 레벨 미터, 결과 게이지 애니메이션 |
| 녹음 | 16kHz/Mono WAV, 최소 길이 강제(검증 3초/등록 5초), 실시간 dBFS 피드백 |
| 검사 | 최소 길이 미달 시 **서버로 보내지 않고** 즉시 안내 |
| 권한 | Android RECORD_AUDIO/INTERNET, iOS·macOS 마이크 설명, macOS 네트워크 엔타이틀먼트 |
| 테스트 | 59개 통과, `flutter analyze` 0 issues |
| **실서버 E2E** | 등록 → 동일 화자 통과 → 타 화자 거부 → 미등록 반려 → 재등록 대체 (LibriSpeech 실측) |

**구현 중 확정한 설계 판단**

*   **Tolerant Reader를 코드로 강제했다.** 응답 파싱이 알 수 없는 필드를 무시하고, 반려 코드에 `unknown`을 두어 서버가 새 사유를 추가해도 앱이 깨지지 않는다. Phase 8의 `spoof_score`가 먼저 배포돼도 앱 재배포가 필요 없다 — 01 §2의 "확장 여지"를 코드 수준에서 실현한 것이다.
*   **앱이 서버보다 먼저 막는다.** 짧은 녹음을 보내면 왕복 후에야 반려를 듣게 되므로, 클라이언트 최소 길이를 서버 하한(1.5초)보다 넉넉히(3초/5초) 잡고 완료 버튼을 잠근다. VAD가 무음을 걷어내면 녹음 길이보다 짧아지기 때문이다.
*   **판정 신뢰도가 낮은 상태를 UI에 드러낸다.** 서버가 AS-Norm 없이 폴백하면 결과 화면에 경고를, 상단 배너에 서버 상태(정규화 꺼짐·임시 저장소)를 표시한다.
*   **"확률"이라 쓰지 않는다.** `match_probability`는 판정 경계를 50%에 맞춘 재척도이므로 UI 표기는 "일치도"이며, 위젯 테스트가 "확률" 문구의 부재를 검사한다.
*   **임시 파일 삭제를 `finally`로 보장한다.** 전송 성공·실패 어느 경로에서도 생체정보를 기기에 남기지 않으며(FR-02), 테스트가 두 경로를 모두 확인한다.
*   **녹음기를 인터페이스로 분리했다.** 마이크는 테스트에서 쓸 수 없으므로 `FakeRecorder`를 주입해 상태 전이와 뒷정리를 검증한다.

### 남은 한계

*   **실기기 검증 미완료.** 마이크 캡처는 `FakeRecorder`로 대체했다. `record` 패키지의 실제 동작(권한 팝업, 기기별 샘플레이트 지원)은 실기기에서 확인해야 한다.
*   사용자 ID가 `demo-user`로 하드코딩되어 있다 — 실제로는 로그인 세션에서 온다.
*   스푸핑 차단 UX(FR-18)는 서버 Phase 8 이후 추가한다.

*   *Micro-process:* Next.js로 관리자 웹 구축, 통계·로그·품질 지표 시각화.

### 구현 결과 (`web/` + `server/app/api/admin.py`)

| 화면 | 내용 |

| `/speakers` | 화자 DB — 등록 현황, 모델/차원, **재등록 필요 여부 자동 감지** |

| 항목 | 결과 |
| :--- | :--- |

### ⚠ 구현 중 드러난 핵심 제약 — 운영 로그로는 FAR/FRR을 계산할 수 없다

03 §4는 "EER/minDCF 추적"과 "FAR/FRR 곡선"을 대시보드 기능으로 적었으나, **감사
로그에는 정답 레이블이 없다.** 검증을 시도한 사람이 실제로 본인이었는지 서버는 알
수 없으므로, 운영 데이터만으로는 오수락·오거부를 셀 수 없다.

따라서 대시보드는 두 종류의 근거를 **엄격히 구분**한다:

| 근거 | 출처 | 말할 수 있는 것 |
| :--- | :--- | :--- |
| 오프라인 캘리브레이션 | `eval/` (레이블 있음) | EER, minDCF, 임계값 결정 |
| 운영 로그 | `verification_attempts` | 점수 분포, 임계값 변경 시 뒤집히는 건수 |

"판정 통과율"은 정확도가 아니라 사용 패턴 지표이며, 서버가 응답에 경고 문구를 실어
보내고 대시보드가 이를 화면에 노출한다. **지표를 오해하지 않게 하는 것이 이 화면의
가장 중요한 일이다.**

### 설계 판단

*   **대시보드가 DB에 직접 붙지 않는다.** 03 문서는 Supabase 직접 접근을 상정했으나, 집계 질의를 서버 관리자 API로 옮겼다. ① 스키마 지식을 한 곳에 모아 마이그레이션 시 두 곳을 고치지 않는다(Phase 6의 `vector(192)` → `vector` 변경이 실제로 서버만 고쳐서 끝났다) ② DB 자격증명을 웹 티어에 두지 않는다.
*   **관리자 API는 토큰 미설정 시 503으로 막는다.** 감사 로그와 사용자 ID가 노출되는 경로이므로, 설정을 빠뜨린 배포가 조용히 공개되는 것보다 아예 막히는 편이 안전하다. 토큰 비교는 상수 시간(`secrets.compare_digest`).
*   **관리자 토큰이 브라우저로 나가지 않는다.** 모든 페이지를 서버 컴포넌트로 두고 `NEXT_PUBLIC_` 접두사를 쓰지 않아 이를 강제한다.
*   **임계값 런타임 변경 API를 만들지 않았다 (FR-11 해석).** 조정 근거(EER·minDCF, 변경 영향도)와 적용 방법(환경변수 스니펫)은 제공하되, 값을 원격에서 바꾸는 API는 두지 않았다. 인증 파라미터를 네트워크로 변경 가능하게 하는 것 자체가 공격면이다.
*   **코호트 집계를 현재 모델로 한정했다.** 초기 구현이 전체 코호트(620개)를 셌으나, 실제 정규화에 쓰이는 것은 현재 모델의 310개뿐이라 오해를 부르는 수치였다.

### 남은 한계

*   **자동 새로고침이 없다.** 03 §3의 "실시간 시각화"는 폴링·SSE가 필요하며, 요청량이 늘어난 뒤 붙이는 것이 맞다.
*   **관리자 계정 체계가 없다.** 단일 공유 토큰이며 접근 감사가 없다.
*   **Phase 7~8 지표(전처리 품질 SI-SNRi, 스푸핑 로그·경보)는 해당 기능이 서버에 들어온 뒤 추가한다** (03 §5).

## Phase 5: 서버 최적화 및 네트워크 지연 최소화 (Week 9-10) — ✅ 완료

### 🐛 최우선 발견 — 동시 요청의 절반이 실패하고 있었다

벤치마크를 돌리자마자 **동시 요청 2건부터 서버가 500을 냈고 세그폴트까지
관측**됐다. 원인은 silero-vad의 TorchScript 모델이 **내부에 RNN 상태를
들고 있다는 것**(`self._state`)이었다. 한 인스턴스를 여러 워커 스레드가 동시에
쓰면 상태가 깨진다.

실측: 동시 요청 4건 중 **2건이 500**.

단일 요청만 테스트했기에 지금까지 드러나지 않았다. **스레드별 모델 인스턴스**로
격리해 해결했고(`threading.local`), 회귀 방지 테스트 6개를 추가했다. 락으로
직렬화하지 않은 이유는 VAD가 파이프라인의 60%를 차지해 처리량이 그대로 막히기
때문이다.

### 구현

| 항목 | 내용 |
| :--- | :--- |
| VAD 스레드 격리 | `threading.local` 기반 스레드별 인스턴스 (동시성 버그 수정) |
| VAD ONNX 전환 | `load_silero_vad(onnx=True)` — 2배 속도, 동일 결과 |
| 추론 동시성 상한 | `VG_MAX_CONCURRENT_INFERENCE=4` — 초과분은 대기열로 |
| 벤치마크 하네스 | `eval/bench.py` — 단계별·동시성·페이로드 측정 |
| 테스트 | 120개 통과 (동시성 6개 신규) |

**설계 판단**

*   **추론 동시 실행에 상한을 둔다.** CPU 바운드라 무제한으로 풀면 처리량은 그대로인데 지연만 늘어난다(개선 전 동시 16에서 p50 1267ms). 상한을 두면 초과분이 대기열에서 기다리므로 **처리 중인 요청은 빠르게 끝나고 꼬리 지연이 예측 가능**해진다. 세마포어를 스레드 진입 전에 잡아 스레드가 쌓이지 않게 했다.
*   **VAD 상태를 매 호출 초기화한다.** 스레드별 인스턴스를 써도 같은 스레드가 요청을 이어 받으므로, 직전 요청의 RNN 상태가 섞이지 않게 `reset_states()`를 호출한다.
*   **동시성 테스트는 값까지 확인한다.** 상태 오염은 예외 없이 **조용히 다른 결과**를 낼 수도 있고 그쪽이 더 위험하다. 점수 일치까지 검사한다.

### 남은 한계

*   **gRPC는 도입하지 않았다.** 계획서의 "필요시" 조건이 아직 아니다 — 현재 병목은 네트워크가 아니라 CPU 추론(87.6ms 중 99%)이며, gRPC는 직렬화 오버헤드만 줄일 뿐이다. 실시간 연속 검증으로 확장할 때 재검토한다.
*   ~~클라이언트 FLAC 전송은 미적용~~ → **적용 완료 (2026-09-01)**. `record` 패키지가 Android·iOS·Windows·macOS·Linux 5개 타깃 모두 FLAC을 지원함을 확인하고, 런타임 `isEncoderSupported` 조회 후 FLAC을 쓰되 미지원 시 WAV로 폴백하도록 구현했다. 실서버 E2E에서 **151KB → 92KB(61%)이면서 `raw_cosine`이 0.772225로 완전히 동일**함을 확인했다. 지원하지 않는 포맷으로 녹음을 시도하면 녹음 자체가 실패하므로 무조건 전환하지 않고 협상하는 구조를 택했다.
*   **단일 프로세스 기준 측정이다.** 다중 워커(`--workers N`) 구성에서는 프로세스당 모델이 중복 적재되므로 메모리와 처리량을 다시 재야 한다.
*   상한 4는 24코어 기준이다. 다른 환경에서는 `eval/bench.py`로 포화 지점을 다시 측정해 정한다.

### 원 계획
*   *Micro-process:* 클라이언트 체감 속도 향상을 위해 오디오 전송 압축, FastAPI 워커(Worker) 수 조정, 네트워크 응답 지연(Latency) 개선. (필요시 gRPC 통신으로 업그레이드).
*   *성능 개선 참조 자료:* 장시간 오디오 처리 비용·지연이 병목으로 확인되면 [chunked-preprocess-pattern.md](chunked-preprocess-pattern.md)(SEP v2/LEP v2 검증 패턴)를 검토한다. 클라이언트 측 겹침 분할 + 조각별 선처리 결과 재사용으로 재분석 비용을 제거하는 방식이며, 현행 02 §2.4 설계를 대체하는 것이 아니라 그 바깥 계층으로 얹는 구조를 상정한다. **현 시점에는 도입하지 않고 보관한다.**

### ✅ Micro-process 1: WeSpeaker 코어 전환 (2026-08-31)

SpeechBrain ECAPA-TDNN(192차원) → **WeSpeaker ResNet34-LM ONNX(256차원)**.

| 항목 | SpeechBrain | WeSpeaker | 판정 |
| :--- | ---: | ---: | :--- |
| AS-Norm EER (K=200) | 1.25% | **1.25%** | 동률 |
| AS-Norm minDCF (K=200) | **0.0317** | 0.0392 | SpeechBrain 우세 |
| 원시 코사인 EER | 1.67% | **1.42%** | WeSpeaker 우세 |
| 분리도 | 4.80 | **5.45** | WeSpeaker 우세 |
| 추론 (5.9초 오디오, 4스레드) | 104ms | **58ms** | **1.8배 빠름** |
| 모델 적재 | 2.06s | **0.25s** | **8배 빠름** |
| 서버 기동 / 검증 지연 (E2E) | 4초 / 273ms | **2초 / 116ms** | 2.4배 빠름 |

**전환 근거는 정확도가 아니라 속도와 배포 무게다.** EER은 동률이며, 2,400트라이얼에서
0.17%p 차이는 **오류 4건 수준의 통계적 잡음**이라 우열을 가릴 수 없다. 반면 스레드
수를 맞춘 추론은 1.8배 빠르고, ONNX 런타임이라 추론에 PyTorch가 필요 없다.

> **측정 함정 한 건:** 최초 벤치마크에서 WeSpeaker가 3배 느리게 나왔는데, ONNX
> 스레드를 1로 고정한 반면 PyTorch는 전체 코어를 쓴 탓이었다. 조건을 맞추자 결과가
> 역전됐다. 스레드 수는 이후 `VG_ONNX_INTRA_OP_THREADS`로 설정 가능하게 했다.

**전환에 따른 변경**

*   `app/services/embedding.py`를 백엔드 플러그인 구조로 재작성 (`speechbrain` | `wespeaker`).
    WeSpeaker는 80차원 Kaldi fbank + CMN을 직접 계산해 ONNX에 넣는다 — CMN을 빠뜨리면
    임베딩이 조용히 나빠지고 오류가 나지 않아 눈에 띄지 않는다.
*   **마이그레이션 003**: `vector(192)` 고정을 풀어 차원 무제약 `vector`로 변경. 1:1 검증은
    ANN 인덱스가 필요 없으므로 가능한 선택이며, Phase 7의 추가 백본 교체에도 대응한다.
    기존 192차원 데이터는 보존된다.
*   **재등록 안전장치가 실전에서 작동했다.** 전환 후 기존 192차원 등록자의 검증 요청이
    `model_mismatch` 422로 정확히 반려됐다 — Phase 2에서 만든 장치가 첫 실사용에서
    제 역할을 확인했다.

### ⚠ Micro-process 2: DeepFilterNet — 측정 결과 **채택 보류** (2026-08-31)

음성 향상을 구현하고 SNR별로 효과를 측정한 결과, **모든 소음 조건에서 EER이
악화됐다.** 기본값을 비활성(`VG_ENHANCE_ENABLED=false`)으로 두고, 근거 없이
켜지 않도록 문서에 명시했다.

WeSpeaker 백엔드, dev-clean 20화자 600트라이얼. 등록은 항상 깨끗한 원본, 검증
발화에만 소음을 주입:

| 조건 | 향상 없음 EER | 향상 적용 EER | 변화 | 분리도 변화 | minDCF 변화 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| clean | 0.33% | 0.33% | 동일 | 5.27 → 5.25 | 0.0267 → **0.0100** |
| SNR 20dB | 2.00% | 2.37% | **악화** | 4.77 → 4.54 | 0.0533 → 0.0777 |
| SNR 10dB | 4.07% | 5.42% | **악화** | 4.18 → 3.47 | 0.1385 → 0.2635 |
| SNR 5dB | 5.15% | **8.47%** | **크게 악화** | 3.92 → 2.89 | 0.2014 → 0.4223 |
| SNR 0dB | 8.23% | 9.08% | **악화** | 3.31 → 2.49 | 0.2765 → 0.5208 |

**분리도가 일관되게 떨어진다**는 점이 핵심이다 — 향상이 genuine/impostor 간격을
좁히고 있다. 즉 소음만 제거하는 것이 아니라 **화자 고유 특징까지 함께 지운다.**
DeepFilterNet은 인지 품질(PESQ/STOI)을 최적화하도록 학습된 모델이지 화자 정체성
보존을 목표로 하지 않으며, 16k→48k→16k 리샘플링 왕복도 아티팩트를 더한다.
처리 비용도 2.8배(13초 → 36초) 든다.

**연구 보고서(『음성 분리 및 화자 대조』 §3.1)는 DeepFilterNet 결합을 권고했지만,
화자 검증 EER 기준으로는 실측이 이를 지지하지 않는다.** 보고서의 근거는 인지 품질과
"노이즈가 임베딩을 오염시키는 것을 차단"이라는 선험적 추론이었고, 실제로 재보니
향상 자체가 더 큰 오염원이었다.

**단서 두 가지**
*   깨끗한 조건에서는 minDCF가 개선됐다(0.0267 → 0.0100). EER은 동일하므로 판정
    경계 근처가 아닌 꼬리 분포가 정리된 것으로 보인다. 다만 이 하나로 채택을
    정당화하기엔 근거가 약하다.
*   주입 잡음은 **가우시안 백색잡음**으로, 소음 억제가 가장 잘 다루는 종류다.
    실환경 소음(MUSAN, 잔향)에서는 결과가 다를 수 있다. 다만 **가장 유리한
    조건에서도 악화됐으므로, 이제 입증 책임은 "켜자"는 쪽에 있다.**

**후속 과제:** 향상이 필요하다면 화자 인증용으로 파인튜닝된 모델을 쓰거나, 향상
전후 임베딩을 융합하는 방식을 검토한다. 코드는 유지하되 기본 비활성이다.

### ✅ 캘리브레이션 실측 결과 (2026-08-31)

**데이터:** LibriSpeech (CC BY 4.0). 평가는 dev-clean 40화자 2,400트라이얼
(genuine 1,200 / impostor 1,200), 코호트는 test-clean 40화자 310개.
**두 split의 화자는 겹치지 않는다** — 코호트에 평가 화자가 섞이면 정규화가 자기
자신을 참조해 측정이 무의미해진다.

| 방식 | EER | 임계값 | minDCF | 분리도 |
| :--- | ---: | ---: | ---: | ---: |
| 원시 코사인 | 1.67% | 0.3333 | 0.0617 | 4.80 |
| AS-Norm (K=50) | 1.33% | 2.3335 | 0.0408 | 3.74 |
| AS-Norm (K=100) | 1.25% | 2.7029 | 0.0383 | 3.90 |
| **AS-Norm (K=200)** ← 채택 | **1.25%** | **3.0033** | **0.0317** | 4.36 |
| AS-Norm (K=300) | 1.25% | 2.8819 | 0.0325 | 4.63 |

**AS-Norm 적용으로 EER 1.67% → 1.25% (25% 개선), minDCF 0.0617 → 0.0317 (49% 개선).**

K 선정: EER이 100/200/300에서 동률이었고, 그중 minDCF가 가장 낮은 K=200을 택했다.
minDCF는 사칭 시도가 드문 실제 환경을 반영해 FAR에 더 큰 가중을 두므로 인증
시스템에 더 적합한 기준이다.

### ⚠ Phase 2 경고가 실측으로 확인됨

Phase 2에서 "임계값 0.25는 미캘리브레이션"이라고 경고한 것이 수치로 확인됐다.

**100번 중 6~7번 타인을 통과시키는** 수준이다. 캘리브레이션 후 기본값을 갱신했다.

| `VG_MATCH_THRESHOLD` (원시 코사인 폴백) | 0.25 (관례값) | **0.3333** (EER 지점) |
| `VG_ASNORM_TOP_K` | — | **200** |
| `VG_ASNORM_THRESHOLD` | — | **3.0033** (EER 지점) |

| 감사 로그 | `normalized_score` 컬럼 실제 기록 시작 (Phase 2에서는 NULL이었음) |
| 테스트 | 69개 통과 (AS-Norm 단위 11 + 통합 7 신규) |
| E2E 실측 | 실제 LibriSpeech 화자로 동일인 통과(정규화 11.46) / 타인 2건 거부(-2.22, -3.00) |

**구현 중 확정한 설계 판단**

*   **정규화 점수와 원시 코사인은 임계값을 공유하지 않는다.** 정규화 점수는 코호트
    표준편차 단위라 코사인처럼 [-1,1]에 갇히지 않는다(실측 genuine 11.46). 두
    임계값을 별도 설정으로 분리하고 문서에 교차 사용 금지를 명시했다.
*   **코호트가 없으면 원시 코사인으로 폴백하되 그 사실을 드러낸다.** 응답의
    `scoring_method`와 `/health`의 `asnorm_active`로 노출한다. 정규화가 꺼진 채
    운영되는 것을 모르고 지나치는 것이 가장 위험하다.
*   **평가는 운영 경로와 같은 조건으로 한다.** `eval/extract.py`는 서버와 동일하게
    VAD를 적용하고, VAD가 반려했을 발화는 트라이얼에서도 제외한다.

### 남은 한계

*   **LibriSpeech는 낭독 음성이다.** 조용한 환경의 또렷한 영어 오디오북이며, 실제
    서비스의 잡음·짧은 발화·다국어 조건과 다르다. 이 임계값은 **출발점이지 최종값이
    아니며**, 운영 데이터가 쌓이면 그 분포로 재캘리브레이션해야 한다.
*   화자 80명은 통계적으로 넉넉하지 않아 임계값 추정치에 표본 오차가 있다.
*   코호트가 LibriSpeech 화자라 실사용자 집단과 음향 특성이 다르면 정규화 효과가
    측정값보다 작을 수 있다.

### 원 계획 (Micro-process 1·2는 미착수)

*   *Micro-process 1 (코어 전환):* 임베딩 엔진을 SpeechBrain → **WeSpeaker**로 전환. SpeechBrain에는 AS-Norm과 서빙 계층이 없어 Phase 6 요구사항을 충족할 수 없으므로, 이 시점이 전환 마감선이다. 전환 시 기존 등록 벡터의 재등록(Re-enrollment) 마이그레이션 수행.
*   *Micro-process 2:* DeepFilterNet(v3) 소음 억제를 VAD 다음 단계에 결합. PESQ/STOI로 향상 전후 품질 비교 검증. 생성형 향상 모델(resemble-enhance 등)은 성문 왜곡 위험 때문에 배제.
*   *Micro-process 3:* 임포스터 코호트 임베딩 DB 구축(공개 데이터셋 활용, 사용자 DB와 격리) 후 WeSpeaker `bin/score_norm.py`를 활용해 AS-Norm 대칭 정규화 스코어링 구현 (자체 구현 대신 검증된 구현체 이식).
*   *Micro-process 4:* 자체 평가 트라이얼 셋 구성 → EER·minDCF 측정 스크립트 작성 → 웹 대시보드에 임계값 캘리브레이션 UI 추가.
*   *Vertical Slice:* 동일 검증 요청에 대해 원시 점수와 정규화 점수를 병기 반환·로그하고, 정규화 적용 전후 EER 개선을 수치로 확인.

## Phase 7: 다중 화자 대응 — 음성 분리 / TSE (확장 Phase C) — ✅ 완료

### 실측 결과 (2026-08-31)

LibriSpeech 16화자, **0dB SIR 2인 혼합** 32트라이얼 (가장 어려운 조건 — 한쪽이
크면 분리 없이도 풀린다). 등록은 항상 깨끗한 발화:

| 조건 | EER | minDCF | 분리도 | genuine 평균 |
| :--- | ---: | ---: | ---: | ---: |
| 깨끗 (상한선) | 3.12% | 0.0312 | 4.98 | 0.711 |
| **혼합 (하한선)** | **15.62%** | 0.3438 | 2.17 | 0.439 |
| **분리 + 선택** | **6.25%** | 0.0625 | 4.08 | 0.588 |

**분리가 EER을 15.62% → 6.25%로 60% 개선**했다. 깨끗한 조건과의 잔여 격차
3.12%p가 **분리 아티팩트로 잃는 양**이며, 02 §4.3이 예고한 임베딩 왜곡이 실제로
그만큼 존재한다는 뜻이다.

**타겟 선택 정확도 100%** (평균 마진 0.492) — 순열 문제를 실용적으로 해결했다.

### 설계: "진짜 TSE"가 아니라 "분리 + 화자 선택"

02 §2.3은 등록 임베딩을 분리망에 **조건으로 주입**하는 TSE를 권장했으나, 구현체
후보 `wenet-e2e/wesep`은 **라이선스 파일이 없어** 채택 전제 조건을 만족하지
못한다(08 §3). 대안으로 **모든 화자를 분리한 뒤 등록 성문과 대조해 고르는** 방식을
택했다.

조건부 분리가 아니므로 비타겟 화자를 능동적으로 억압하지는 못하지만, **순열 문제를
없앤다는 실용적 목표는 동일하게 달성**하며 라이선스가 명확한 Apache-2.0 모델만 쓴다.
wesep 라이선스가 확인되면 교체할 수 있도록 인터페이스를 "혼합 + 등록 임베딩 →
타겟 파형"으로 두었다.

### 분리 모델: ClearerVoice → SepFormer로 변경

Phase 6 조사는 ClearerVoice-Studio(MossFormer2-SS)를 1순위로 적었으나, 실제 설치
검토 결과 `clearvoice` 패키지가 **opencv·torchvision·scenedetect 등 영상 처리
의존성을 끌어오고 soundfile을 다운그레이드**한다. 파이프라인이 의존하는 패키지라
위험이 이득보다 크다고 판단해 이미 검증된 SpeechBrain **SepFormer(whamr16k)**를
채택했다. 16kHz라 리샘플링 왕복이 없고 잡음·잔향 조건으로 학습됐다.

분리 품질 실측: 2인 혼합에서 화자별 SI-SNR +8.71dB / +9.70dB (혼합 대비 약 +9dB
개선), 교차 누설 -35~-50dB.

### 🐛 발견·수정한 성능 버그 — silero-vad의 전역 스레드 변경

E2E에서 검증 응답이 **30초**가 나왔다(분리 없을 때 116ms의 250배). 추적 결과
**silero-vad가 `torch.set_num_threads(1)`을 호출해 프로세스 전체를 단일 스레드로
낮추고 있었다.** VAD 자체는 가벼워 스스로는 문제가 없지만, 같은 프로세스의 분리
추론이 4배 느려진다.

증상이 교묘했던 이유: 첫 요청은 분리가 VAD보다 먼저 실행되어 7.6초로 정상이었고,
**두 번째 요청부터** 30초가 됐다. 부하가 아니라 순서 때문이었다.

`app/services/vad.py`에 스레드 수를 보존하는 컨텍스트 매니저를 두어 격리했다.
라이브러리가 전역 상태를 바꾸는 것은 고칠 수 없으므로 경계에서 막는다.

**수정 효과: 30초 → 6.9초 (4.3배).** 이 버그는 Phase 1~6의 서버 지연 측정에도
영향을 줬을 것이다(SpeechBrain 백엔드 시절 359ms·273ms는 1스레드 상태였다).
정확도 측정은 영향받지 않는다.

### 구현 결과

| 항목 | 결과 |
| :--- | :--- |
| 분리 서비스 | `app/services/separation.py` — 분리 + 등록 성문 기반 타겟 선택 |
| 응답 확장 | `separation` 필드 (출력 수, 선택 인덱스, 유사도, **선택 마진**) |
| 검증 경로 | 등록 성문을 먼저 조회하도록 순서 재구성 (분리에 필요) |
| 평가 하네스 | `eval/separation_eval.py` — clean/mixed/separated 3조건 비교 |
| 테스트 | 101개 통과 (분리 10개 신규) |
| E2E 실측 | 2인 혼합 검증 통과, 6.9초, 선택 마진 0.642 |

**설계 판단**

*   **기본값은 비활성(`VG_SEPARATION_ENABLED=false`)이다.** 단일 화자 오디오에 분리를 걸면 아티팩트만 더하고(잔여 격차 3.12%p가 그 비용이다), 추론 비용이 크다. 다중 화자가 실제로 섞여 들어오는 배포에서만 켠다.
*   **검증 경로에서만 동작한다.** 등록은 통제된 환경에서 단일 화자로 받는 것이 전제이므로 분리할 이유가 없다.
*   **등록 성문 조회를 오디오 분석보다 앞으로 옮겼다.** 분리에 등록 임베딩이 필요하기도 하고, 미등록·모델 불일치를 먼저 걸러내면 헛된 추론 비용도 아낀다.
*   **선택 마진을 응답에 노출한다.** 1등과 2등의 유사도 차이가 작으면 어느 출력이 타겟인지 모호했다는 뜻이므로, 판정 신뢰도를 낮게 봐야 한다는 신호다.

### 남은 한계

*   **CPU 추론 비용이 크다.** 6초 오디오 분리에 약 7초(RTF 1.2)가 걸려 대화형 인증에는 여전히 부담이다. GPU를 붙이거나, 다중 화자가 감지될 때만 선택적으로 적용하는 게이팅이 필요하다.
*   **2화자 고정 모델이다.** 3인 이상 혼합은 SepFormer whamr16k가 다루지 못한다.
*   **아티팩트 증강 파인튜닝(Micro-process 3)은 미착수.** 잔여 격차 3.12%p를 줄이려면 분리 출력으로 임베딩 백본을 파인튜닝해야 한다. 251화자 ArcFace 학습을 CPU로 하면 수일이 걸려 현 환경에서는 비현실적이다.

    **대안 시도 (2026-09-01) — 결론 내지 못함.** 학습 없이 같은 문제를 겨냥해,
    AS-Norm 코호트를 분리를 거친 오디오로 만들어 검증 조건과 맞추는 방법을
    실험했다(`eval/separation_cohort_eval.py`). 관측값:

    | 검증 조건 | 정규화 없음 | 깨끗한 코호트 | 분리 코호트 |
    | :--- | ---: | ---: | ---: |
    | 깨끗 | 1.60% | 1.67% | 1.67% |
    | 분리+선택 | 1.80% | 3.33% | 2.98% |

    분리 코호트가 깨끗한 코호트보다 나아 보이지만(3.33% → 2.98%), **이 측정으로는
    어느 쪽도 주장할 수 없다.** 두 가지 결함 때문이다:

    1. **표본 부족** — genuine 60건이라 EER 해상도가 1.67%p인데, 관측된 차이는
       1.53%p로 그보다 작다.
    2. **코호트 부족** — 코호트 90개에 top_k 200이라 `min(200, 90) = 90`으로
       전체를 쓰게 됐다. 상위 K를 적응적으로 고르는 것이 AS-Norm의 핵심인데
       그 부분이 무력화돼, 운영 설정(코호트 310 / K 200)과 다른 것을 잰 셈이다.

    첫 시도는 트라이얼 40건으로 세 조건이 모두 5.00%로 나왔는데, 이는 개선이
    없다기보다 해상도(2.5%p)가 차이보다 커서 **측정 자체가 불가능**했던 것이다.
    impostor를 1건에서 전 화자로 확장해(분리 추론은 비싸지만 내적은 싸다) 검정력을
    높였으나 genuine 쪽은 여전히 부족했다.

    실험 도구에 **결론 가능성 검사**를 넣었다 — 코호트가 top_k 대비 작거나 관측된
    차이가 해상도보다 작으면 경고를 내고 `conclusive: false`로 기록한다. 없는
    효과를 있다고 읽는 것을 막기 위해서다. 제대로 결론을 내려면
    `--per-speaker`와 `--cohort-speakers`를 크게 잡아 다시 돌려야 하며,
    분리 추론이 트라이얼당 약 7초라 상당한 시간이 든다.
*   평가가 16화자 32트라이얼로 작아 표본 오차가 크다.

### 원 계획
*   *Micro-process 1:* **ClearerVoice-Studio(MossFormer2-SS, 16kHz)** 사전학습 모델로 2인 혼합 오디오 분리 PoC. 프레임워크를 SpeechBrain으로 통일하는 편이 유리하다고 판단되면 SepFormer로 대체. Mamba 계열(SPMamba 등)은 CUDA 커널 의존으로 CPU 추론이 불가하므로 GPU 상시 확보 전까지 후보에서 제외.
*   *Micro-process 2:* 등록 임베딩을 조건으로 하는 타겟 화자 추출(TSE) 방식 실험 — 순열 문제 회피 및 파이프라인 단순화 비교. 후보 `wenet-e2e/wesep`은 **착수 전 라이선스 확인이 선행 조건**(저장소에 LICENSE 파일 없음).
*   *Micro-process 3:* **임베딩 왜곡 대응:** 분리망 출력 아티팩트를 첨가한 증강 데이터로 임베딩 백본 파인튜닝(탈동조화 전략). 이 시점에 백본을 단기 발화에 강한 ERes2NetV2(3D-Speaker)로 교체 평가 (교체 시 기존 사용자 재등록 마이그레이션 절차 수행).
*   *Vertical Slice:* 2인 동시 발화 녹음 → 분리 → 타겟 화자 검증 성공률을 단일 화자 대비 벤치마크.

## Phase 8: 보안 방어막 — Anti-Spoofing (확장 Phase D) — ✅ 완료

### 실측 결과 (2026-08-31)

**ASVspoof 2019 LA 검증 세트** — TTS·보이스 컨버전 6종(A01~A06)으로 만든 실제
위조 음성이 레이블과 함께 든 표준 벤치마크. 균형 표본 2,000개(bonafide 1,000 /
spoof 1,000), 평균 3.5초.

| 집계 | EER | 임계값 | 분리도 | bonafide 평균 | spoof 평균 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| max | **0.70%** | 0.9224 | 13.46 | 0.0135 | 0.9980 |
| mean | 0.70% | 0.8557 | 14.44 | 0.0121 | 0.9978 |

**운영 지점 (max 집계)**

| 임계값 | 위조 탐지 | 정상 차단 |
| ---: | ---: | ---: |
| 0.50 | 99.9% | 1.20% |
| **0.70** ← 채택 | **99.9%** | **1.00%** |
| 0.90 | 99.4% | 0.90% |
| 0.95 | 99.2% | 0.70% |
| 0.99 | 99.0% | 0.60% |

0.7을 택한 이유: 0.5와 탐지율이 같으면서(99.9%) 정상 차단은 적어 **0.5를
지배**한다. 더 높이면 차단은 줄지만 위조를 놓치기 시작한다.

| 앱 | 차단 시 "직접 말씀해주세요" 안내, 재시도 경로 유지 (FR-18) |
| 테스트 | 서버 114개 + 앱 61개 통과 (안티스푸핑 13개 신규) |
| E2E | 실제 음성 통과(0.0016) / 합성 음성 차단 / 점수 미노출 확인 |

**설계 판단**

*   **탐지를 파이프라인 최전단에 둔다.** 합성 음성이면 이후 분리·임베딩·대조가 모두 무의미하므로 비싼 연산 전에 거른다. 분리보다 앞인 이유는 분리가 원본에 없던 아티팩트를 만들어 탐지기를 혼란시킬 수 있어서다 — 판정은 사용자가 실제로 보낸 신호를 대상으로 해야 한다.
*   **클라이언트에 점수를 노출하지 않는다 (FR-18).** 공격자가 점수를 보고 우회 방법을 탐색하는 것을 막는다. 응답의 `spoof` 필드는 관리자용이며, 차단 시에는 사유 코드와 안내 문구만 간다.
*   **구간별 최댓값으로 집계한다.** 긴 오디오는 여러 구간으로 나눠 점수를 내고 가장 높은 값을 쓴다. 평균을 쓰면 일부만 합성인 공격이 진짜 구간에 희석돼 놓친다.
*   **차단돼도 재시도 경로를 연다.** 정상 사용자가 오탐으로 걸릴 수 있고(1.00%), 실제 공격자에게는 재시도가 무의미하다 — 같은 합성음은 또 걸린다.
*   **기본 비활성.** 가중치를 저장소에 커밋하지 않으므로 내려받지 않은 환경에서 기동이 실패하지 않게 한다. **보안이 필요한 배포에서는 반드시 켠다.**

### 🔴 후속 측정으로 드러난 치명적 문제 — 도메인 불일치 (2026-09-01)

위 "남은 한계"의 첫 항목(긴 오디오 오탐)을 실측한 결과, **예상보다 훨씬 심각하고
원인도 달랐다.** 진짜 사람 음성(LibriSpeech)을 길이별로 재보니 임계값 0.7에서:

| 길이 | 구간 수 | 정상 사용자 차단 |
| ---: | ---: | ---: |
| 4~6초 | 1 | 0% |
| 10초 | 2 | **66.7%** |
| 15초 | 4 | **77.8%** |
| 20~30초 | 5~7 | **88.9%** |

**진짜 사람 음성의 89%가 차단됐다.** 클라이언트는 3~30초를 녹음하므로 배포 불가
수준이었다.

**원인은 두 가지가 곱해진 것이다.**

1. **도메인 불일치 (주원인).** AASIST-L은 ASVspoof 2019 LA로 학습됐고 그 bonafide는
   VCTK 코퍼스다. 다른 녹음 조건의 진짜 음성을 위조로 오인한다 — 구간별 오탐률
   실측: **ASVspoof bonafide 1.0% → LibriSpeech 13.3% (13배)**.
2. **최댓값 집계의 복리.** 구간별 오탐률 p, 구간 n개면 오탐은 1-(1-p)^n로 커진다.
   13.3%가 7구간에서 63%가 된다.

VAD로 무음을 걷어내도 거의 개선되지 않았다(75% → 65%). 무음이 아니라 **녹음 조건
자체**가 원인이라는 뜻이다.

**따라서 Phase 8이 보고한 EER 0.70%는 도메인 안(in-domain) 수치이며, 다른 오디오
도메인으로 이전되지 않는다.** 이 한계를 "ASVspoof 공격만 검증했다"고 적었으나,
bonafide 쪽 도메인 문제는 짚지 못했다.

**조치: 기본 임계값 0.7 → 0.999.** 도메인 밖(LibriSpeech 10초) 실측 운영 지점:

| 임계값 | 정상 차단 | 위조 탐지 |
| ---: | ---: | ---: |
| 0.70 | 58.8% | 100.0% |
| 0.99 | 13.8% | 100.0% |
| **0.999** | **0.0%** | **99.0%** |
| 0.9999 | 0.0% | 91.0% |

0.999로 올린 뒤 **전 길이 구간(4~30초)에서 오탐 0%**를 확인했다. 위조 탐지 99%는
유지된다.

**오탐이 서비스를 망가뜨린다**는 것이 이 선택의 근거다. 정상 사용자를 차단하면
인증 자체를 쓸 수 없게 되는 반면, 0.999에서도 위조는 99% 잡는다. 도메인 안이라면
훨씬 낮은 값이 맞지만(0.7에서 99.9%), **어느 도메인인지 모르는 배포에는 보수적
값이 안전하다.**

`eval/antispoof_length_eval.py`를 추가해 자사 오디오로 재캘리브레이션할 수 있게
했고, 기본 임계값이 0.999 아래로 내려가지 않도록 테스트 가드를 걸었다.

### ⚠ 남은 한계

*   ~~긴 오디오의 오탐 위험을 충분히 재지 못했다~~ → **위에서 측정·해결**.
*   **배포 환경 오디오로 임계값 재캘리브레이션이 여전히 필수다.** 0.999는 LibriSpeech
    기준 안전값이지, 모든 도메인에 맞는 값이 아니다. 마이크·코덱·환경이 다르면
    다시 재야 한다.
*   **근본 해결은 도메인 적응이다.** 임계값 조정은 증상 완화이며, 자사 데이터로
    파인튜닝하거나 일반화가 나은 SSL 계열 모델(XLSR+AASIST)을 쓰는 것이 정답이다.
*   **참고 — 원래 기록:** 최댓값 집계는 구간이 많을수록 하나라도 높게 나올 확률이 커진다. 평가 세트 평균이 3.5초(대부분 1구간)라 이 위험이 반영되지 않았고, 실제로 **12초 LibriSpeech 발화에서 최댓값이 0.79까지 오른 사례**가 있다. 클라이언트는 3~30초를 녹음하므로 **배포 전 자사 오디오 길이 분포로 재측정이 필요하다.**
*   **2차 정밀 판정(XLSR+AASIST) 미착수.** 08 §4의 2단 캐스케이드에서 1차만 구현했다. SSL 프론트엔드가 300M 파라미터라 CPU 지연 예산을 넘는다. AASIST-L 단독으로 EER 0.70%가 나와 우선순위가 낮아졌으나, 미지의 신종 공격 일반화는 SSL 계열이 낫다는 것이 문헌 결론이다.
*   **ASVspoof 2019 공격만 검증했다.** 2019년 이후 TTS는 크게 발전했다. `MuSAELab/AUDDT`(33개 데이터셋)로 교차 일반화를 점검하는 것이 다음 단계다.
*   **재생 공격(Physical Access)은 다루지 않는다.** AASIST-L은 논리적 접근(LA) 전용이다.

### 원 계획
*   *Micro-process 1:* **AASIST-L**(85K 파라미터, CPU 실시간) 사전학습 모델을 검증 파이프라인 초입에 배치, `spoof_score` 임계 기반 1차 차단 로직 구현.
*   *Micro-process 2:* 1차 의심 샘플에 한해 **XLSR + AASIST**(`SSL_Anti-spoofing`) 2차 정밀 판정을 적용하는 캐스케이드 구성. 원본의 fairseq/torch 1.8 고정 의존을 피하기 위해 프론트엔드를 HuggingFace `wav2vec2-xls-r-300m`으로 교체 포팅 (추론 전용이므로 포팅 범위 작음).
*   *Micro-process 3:* TTS 생성 음성으로 자체 공격 시뮬레이션 → 탐지율(EER·F1) 측정. 교차 데이터셋 일반화는 `AUDDT`(33개 데이터셋), 표준 지표 산출은 `asvspoof-challenge/2021` eval-package 사용. **AASIST3는 CC BY-NC-ND 라이선스로 상용 배치가 불가하므로 업그레이드 경로에서 제외.**
*   *Vertical Slice:* 합성 음성 인증 시도가 차단되고 관리자 대시보드에 스푸핑 로그·경보가 표시되는 E2E 확인.
