# BEF2.0 청크 처리 방식 도입 검토 (Open Issue)

## 0. 문서 상태

> **⚠ 미확정 문서.** `BEF2.0`은 본 저장소의 문서·코드 및 워크스페이스 전체 검색에서 발견되지 않은 **외부(사내) 규격**이다. 현재 확보된 정보가 없으므로, 본 문서는 **확인해야 할 항목을 정의한 체크리스트**이며 채워지기 전까지 어떤 항목도 확정 사양으로 인용해서는 안 된다.
>
> 자료(설계 문서·소스·API 스펙) 확보 시 아래 TBD를 채우고, 02 문서 2.4절의 파라미터·인터페이스를 그에 맞춰 재정렬한다.

## 1. 검토 배경

02 문서 2.4절의 CSS(연속 음성 분리) 청크 처리 설계는 **학술 표준 방식**을 근거로 작성되었다. 사내 서버 BEF2.0이 이미 청크 기반 오디오 처리 파이프라인을 운영 중이라면, 본 프로젝트가 별도 방식을 새로 만드는 대신 **BEF2.0 방식을 도입(재사용)하는 편이 유리할 수 있다.** 판단을 위해 다음을 확인한다.

### 2.2 아키텍처 역할 분담
확인 필요 — BEF2.0이 파이프라인에서 어느 위치를 담당하는가?

* ☐ **(A) 입력 계층만 담당:** 오디오 수신·버퍼링·청크 분할까지만 하고, 분리·임베딩·검증은 본 프로젝트 서버가 수행 → 청크 규격만 맞추면 되므로 통합 비용 최소.
* ☐ **(B) 처리 파이프라인 공유:** BEF2.0 위에 본 프로젝트 모듈을 얹는 구조 → BEF2.0의 런타임(언어·프레임워크)과 Python/PyTorch 스택의 호환성 검토 필요.
* ☐ **(C) 별도 시스템:** 청크 처리 *방식(설계 패턴)*만 참조하고 구현은 독립 → 문서만 참고.

## 3. 판단 기준

아래 조건을 **모두** 만족하면 BEF2.0 방식을 도입하고, 하나라도 어긋나면 그 항목만 조정하거나 독립 구현을 선택한다.

1. 겹침 길이가 0.8초 이상이어서 화자 스티칭이 가능하다.
2. 오디오 규격(16 kHz/Mono)을 만족하거나 무손실 변환이 가능하다.
3. 세션 상태 관리 계층을 제공하거나, 본 프로젝트가 외부 저장소로 보완할 수 있다.
4. 종단 지연이 목표 응답 시간 예산 안에 들어온다.

## 4. 대안: TSE 선회

BEF2.0의 청크 규격이 스티칭에 부적합한 것으로 판명되면, **타겟 화자 추출(TSE)** 방식으로 선회하는 것이 유력한 대안이다. TSE는 출력 채널이 항상 1개(타겟 화자)로 고정되므로 **윈도우 간 순열 정렬 자체가 불필요**하고, 따라서 겹침 길이 제약에서 자유롭다. 상세는 02 문서 §2.4.3 참조.
